# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project shape

Envelo is a monorepo, currently two runnable services (the README frames it as a "modular monolith gradually split into microservices" — the Auth/Ingestion/Analytics split in `docs/architecture.md` is aspirational, not yet real):

- `frontend/` — Flet 0.86 (Python) UI, managed with `uv` + `pyproject.toml`. `frontend/requirements.txt` only pins `flet==0.86.2` for reference; it is not the source of truth for deps.
- `services/api-gateway/` — FastAPI + SQLAlchemy 2.0 (async) + Alembic, managed with plain pip + `requirements.txt` (no pyproject.toml here). Holds all budgeting logic today.
- `docs/` — `architecture.md`, `erd.md`, `migrations.md`, and `brandbook.md` (design source of truth for the frontend — see below).

**No CI exists** (`.github/workflows` is absent), so nothing gates a change automatically — but **ruff is configured in both services** and is worth running before you call something done: `[tool.ruff]` in `frontend/pyproject.toml` and `services/api-gateway/ruff.toml`. Both use `line-length = 120` and `select = ["E4", "E7", "E9", "F", "I"]` with `E501` ignored, because declarative UI trees (long single-expression `ft.Container`/`ft.Row` nests) are deliberately left unwrapped. The 5 `I001` findings in `services/api-gateway/migrations/` are pre-existing, in Alembic-generated files — leave them alone rather than reformatting generated history.

Note that an editor/hook may reformat files on save, **including stripping imports that nothing references yet**. When adding an import and its first use in separate edits, expect the import to disappear in between; add the usage first, or re-add the import afterwards.

## Frontend (Flet)

- Two entrypoints that must behave the same but stay separate: `main.py` (used by `flet run` / `flet test`, keeps the `if __name__ == "__main__"` guard) and `asgi.py` (Docker/uvicorn production entrypoint, `export_asgi_app=True`).
- Routing: `routing.py` has `VIEW_BUILDERS` (route → `async def build_x_view(page) -> ft.View`) and `ROUTE_PARENTS` (back-stack parent for routes that shouldn't pop straight to `/`). Add both when adding a route.
- `views/common.py` provides the shared shell: `app_shell()` (main screens with nav) and `standalone_shell()` (Login/First-run, no nav). Both set `padding=0, spacing=0` on the returned `ft.View` deliberately — `ft.View` defaults to 10px of both, which gaps the header from the nav rail. The content column inside is already scrollable (`ft.ScrollMode.AUTO`); views must not set their own `scroll=`.
- No CSS media queries in Flet — responsiveness is driven by `theme.layout_band(page.width)` → `"mobile"/"tablet"/"desktop"`. `page.width` is `None` before the first frame, so band helpers default to desktop. Views are rebuilt on `page.on_resize` only when the band changes, not on every resize.
- Buttons (`components/button.py`) are `ft.Container(ink=True, ...)` wrapping `ft.Text`, not `ft.*Button` widgets — relevant when locating buttons in tests or by control type.
- **Known rendering bug**: an `ft.Row(wrap=True)` whose *direct* children include an interactive control (button `Container`, `ft.Dropdown`, `ft.TextField`) paints as a flat grey box instead of real content, in flet-web and presumably flet-desktop. Nesting the control one level deeper (inside a non-wrap child Row/Column) is fine. Don't put interactive controls as direct children of a `wrap=True` Row — use a fixed/horizontally-scrolling row instead.
- `ft.LineChart`/`ft.BarChart` don't exist in this Flet version (they're in the separate `flet-charts` package, not a dependency here). Charts/graphs are built from `ft.ProgressBar` or plain containers.
- `docs/brandbook.md` is the source of truth for design tokens; `theme.py` ports it 1:1. If they disagree, fix `theme.py`, not the brandbook. Money formatting lives in `currency.py`, not `mock_data.py`: a registry of locales (`pln` is the default — `1 234,56 zł`, non-breaking group space; also `eur-eu`, `eur-us`), switchable at runtime from Settings and persisted to `page.shared_preferences`. Always format through `format_money()`/`format_amount_bare()`; never hardcode a symbol or separator.
- Accounts carry their **own** `currency`; `currency.py` is one reader's display preference for their whole budget. The Accounts screen therefore renders `format_amount_bare(x) + " " + account["currency"]`, and only claims a cross-account total when every account shares a currency. Never format an account balance with `format_money()`.
- One screen hands a search term to another through `views/common.py::PREFILL_SEARCH_KEY` (Payees' "History" → Transactions). It is declared in `common.py` so neither view imports the other, is *consumed* on read so it applies once, and lands in the visible search box — `GET /budget/transactions` has no payee parameter, so this is a search, not an exact filter, and it widens the range to the year so an older payee does not open onto "No transactions match".
- **Session storage is `page.session.store`, not `page.session`** — the latter is Flet's `Session` object and has no `get`/`set`, so `page.session.set(...)` raises at runtime. It carries `selected_envelope_id` across a `page.navigate()` because `routing.py` has no dynamic route segments. It also carries `views/common.py::CATEGORY_GROUPS_COLLAPSED_KEY` (whether the sidebar's category-groups list is expanded — session-scoped, not a `preferences.py` setting, since collapsing a long list is a per-visit convenience, not a choice worth surviving a restart). When stubbing Flet objects in tests, prefer the real class (`flet.messaging.session_store.SessionStore`) over a `SimpleNamespace` with hand-picked attributes — a hand-rolled fake once endorsed this exact nonexistent API and every test passed while the app crashed.
- **Every `on_click` handler takes `e`, with no exceptions** — Flet always calls it with the event object, so a zero-argument lambda type-errors the instant it is actually clicked rather than silently doing nothing. This bit the nav rail's "Settings" link under the username (`components/nav_rail.py`), which looked wired up and crashed on the first real click; `frontend/tests/test_views.py` now clicks it directly rather than only asserting the control tree shape.
- **Mock data is being retired screen by screen.** Already on the real API: everything except **Statements** and **Import**, which still render `mock_data.py` rows (`STATEMENTS`, `IMPORT_ROWS`). Everything else that imports `mock_data` pulls only the pure helpers (`Envelope`/`Transaction`/`EnvelopeView`, `envelope_view()`, `envelope_state()`, `date_short()`), which are presentation types with no mock rows behind them and will move to their own module once the last screen is converted. `GROUP_BAR_COLOR` and `HISTORY` are dead already; `GROUPS`/`all_envelopes()` survive only for `gallery.py` and `views/dialogs.py::_envelope_options`.
- **Forecast renders the server's projection and computes none of its own.** Everything on the screen comes from `GET /budget/forecast`, whose `method` field names the estimator behind it (`"linear-pace"` today). That split exists so a real predictive model can replace the arithmetic without the view changing — so don't reintroduce pacing, ranking or group rollups client-side. Envelope/group *names* still come from `fetch_budget_snapshot()`, since the forecast speaks in ids like every other aggregate. An unknown `method` must be described, not treated as an error.
- **Alerts are computed live from the envelopes; there is no alerts table.** The old mock invented timestamps, a delivery channel and the claim that anything had been sent. Nothing sends notifications, so nothing is stored — persisting these would only cache a pure function of the envelopes. Forecast-based alerts are deliberately absent while the projection is a placeholder.
- `preferences.py` holds the client-side settings that no single module owns — the **alert threshold** and **dark mode** (module-level state + `page.shared_preferences`, same pattern and same single-user caveat as `currency.py`; currency stays where it is because its stored value and its formatters are one concern). `main.py::_restore_preferences` applies all three before the first render, and `theme.apply_theme()` reads `dark_mode()` rather than hardcoding light. Settings has no other live controls: the notification picker is **deliberately disabled** (Envelo has no mailer, webhook worker or queue), and neither Settings nor any other screen may show a user name or email — there is no user entity. `envelope_state()` reads `alert_fraction()` live, so the Settings slider moves Alerts, the Dashboard's heads-ups, the sidebar's attention badge and the amber envelope rows together — never hardcode 80% or 0.8 anywhere. Settings commits on `on_change_end`, not `on_change` (a drag fires ten times and each commit rebuilds the route), and `main.py::_restore_preferences` applies both saved values before the first render. `set_alert_threshold()` clamps and falls back, because the value can arrive from storage. Tests must reset both preferences — `test_views.py` has an autouse `reset_preferences` fixture, since a leaked threshold repaints envelopes in unrelated tests.
- `views/common.py::fetch_budget_snapshot()` is the shared read for anything envelope-shaped: it returns a `BudgetSnapshot` and is handed to `app_shell(..., snapshot=...)` so the nav rail doesn't re-fetch what the screen already has. Dashboard and Envelopes both do this; new envelope-shaped screens should too.
- **Money rolls over.** `Envelope.assigned` and `Envelope.spent` are **this month's** figures; `carried_over` is what was left when the month began; `funded` (= carried_over + assigned) and `available` (= funded − spent) are properties. Measure states, bars and "over" against `funded`, never against `assigned` alone. The three are kept apart on purpose: the Ledger's Assigned field is editable and writes *this month's* allocation row, so a field showing a running total would save a monthly one and wipe out the difference. What makes the arithmetic close is `cash = to_assign + sum(available)` — verified against live data, drift 0,00.
- `api_client` never raises: reads return `[]`/`{}`/`0` and writes return `None` on failure. To tell "empty" from "unreachable", wrap the fetch in `api_client.collect_failures()` and render `components/notice.py::notice_banner` when it reports anything — the block must enclose the `asyncio.gather`, since tasks copy the context at creation. A 404 is not a failure: the gateway answers "no rows" with 404 on most list endpoints.
- `gallery.py` is a standalone visual QA screen showing every component (`flet run src/gallery.py`) — not part of the routed app.

## Backend (api-gateway)

- All FastAPI routes for every entity live in the single `app/main.py` (~580 lines) — there is no `app/routers/` package. Only the repository layer (`app/db/repositories/`) is split one file per entity.
- **Most list endpoints answer an empty result with 404, not `[]`** (accounts, payees, category groups, envelopes, allocations, statements, rules). `GET /budget/transactions` and `/spent-by-envelope` deliberately return `[]` instead. Frontend code must not read a 404 as an error.
- Five aggregates exist: `GET /budget/transactions/spent-by-envelope` (`SUM(-amount)` per envelope, positive, excludes uncategorized rows), `GET /budget/envelope-allocations/to-assign`, `GET /budget/forecast`, `GET /budget/accounts/balances` and `GET /budget/payees/stats`. `to-assign` satisfies `cash = to_assign + sum(available)`, which is why it adds envelope-charged spending back: a categorized purchase leaves the account *and* the envelope, so subtracting `sum(assigned)` alone counts it twice. Monthly summaries and per-group rollups outside the forecast do **not** exist yet.
- The three list-shaped aggregates (`balances`, `payees/stats`, and the forecast's rows) all return **every** row of their entity, including ones with no activity, and answer an empty database with `[]` rather than 404 — otherwise a screen built on one would silently disagree with the plain list endpoint next to it. `balances.balance` and `payee stats.total` are **signed** sums, not amounts spent: a credit card in debt and an employer paying you are both normal.
- `POST /budget/payees/merge` repoints one payee's transactions onto another and deletes it. It exists because imports create a payee per spelling ("BIEDRONKA 1234" vs "Biedronka"), which splits the very history `match_envelope_for_transaction` relies on. Merging into itself is a 400.
- `GET /budget/forecast` (`app/db/repositories/forecast.py`, its own module because it reads two entities and owns no table) is the seam a predictive model plugs into. It returns per-envelope and per-group projections plus totals, with `method` naming the estimator — replace `_project` and bump `LINEAR_PACE`, and no client changes. `asOf` pins the anchor day (clamped into the month) so the figure is reproducible and testable without freezing the clock; `elapsed_fraction` is rounded *before* use so `spent / elapsed_fraction == projected` holds for anyone checking. It answers an empty budget with zeroed totals, not 404. The comparison baseline is `funded`, never `assigned` alone.
- **Don't hard-code seeded row ids in tests.** Several test files borrowed `SEEDED_ENVELOPE_ID = ...0401` ("Groceries"), which was only safe while the API refused to delete an envelope that had allocations. Deleting one is allowed now (it uncategorizes the transactions), so when that row was deleted from the dev database 11 unrelated tests failed on a 409. Create what a test needs — `SEEDED_CATEGORY_GROUP_ID` and `SEEDED_ACCOUNT_ID` are still borrowed, but everything below them is built per test and rolled back.
- There is no auth and no user entity in any schema: every repository hard-codes `SEED_USER_ID` from `app/db/repositories/constants.py`.
- Repository functions call `db.commit()` themselves, not the router — relevant when reasoning about transaction boundaries or test rollback behavior.
- Route path params are `camelCase` (e.g. `/{accountId}`) to match frontend/JS conventions, even though function/variable names stay `snake_case` — a deliberate PEP8 mismatch, not an inconsistency to fix.
- Categorization: `match_envelope_for_transaction()` (`app/db/repositories/categorization_rule.py`) matches `CategorizationRule.phrase` against the **payee's name** (case-insensitive substring, longest phrase wins on ties), and only then falls back to the payee's most-frequent past envelope. **An explicit rule beats inferred history** — since both key off the payee, the other order would mean a rule for an already-filed payee never fires. Rules do not look at the description at all, so a CSV with no payee column cannot be filed by rules; there is no rule ordering, no payee/amount conditions, and nothing records which rule filed which transaction (hence no "matches" count on the Rules screen).
- Alembic: run from `services/api-gateway` (`alembic upgrade head`, `alembic revision --autogenerate -m "..."`). `alembic_version` intentionally lives in the `budget` schema, not `public`. `migrations/env.py` builds the DB URL from `Settings`, not `alembic.ini`.

## Testing

- Backend tests (`services/api-gateway`, run via `pytest`) use a **real Postgres**, not mocks — `tests/conftest.py` wraps each test in a transaction with a `SAVEPOINT` that's rolled back after, so `db.commit()` calls never actually persist. Assume Postgres is already running (`docker compose up -d postgres`) rather than starting it yourself.
- `pytest.ini` sets `asyncio_mode = auto`.
- Frontend tests (`frontend`, run via `uv run pytest`): `test_routing.py`, `test_mock_data.py`, `test_api_client.py`, `test_views.py` are pure/logic-level and reliable locally. `test_views.py` stubs the API per view module (`monkeypatch.setattr("views.dashboard.get_payees", ...)`), not on `api_client`, because views do `from api_client import ...` and bind their own reference at import time; the shared shell reads are stubbed on `views.common`. When a stub can return different values for different arguments, make it do so — a stub that ignored its date arguments once let two "passing" tests cover none of the behaviour they named. `test_main.py` drives a real rendered Flet app via the `flet[test]` integration-test plugin — on this machine it fails with "Building with plugins requires symlink support" because **Windows Developer Mode is disabled**. Treat `test_main.py` failures as this known environment limitation, not a code bug, unless Developer Mode has since been enabled.
